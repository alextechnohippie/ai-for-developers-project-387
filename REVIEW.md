# REVIEW.md — критерии независимого ревью

Критерии для авторевью PR календаря звонков. Ревьюер читает этот файл из **базовой** ветки:
PR не может подменить критерии для самого себя.

## Что считается дефектом

- Занятый слот остаётся доступным для повторной записи.
- Пересечение записей разных типов встреч.
- Слот вне рабочих часов или вне окна записи.
- Потеря или искажение данных записи (в том числе новой темы разговора).
- Поведение не соответствует согласованной спецификации или выходит за объём, зафиксированный
  в комментарии согласования.
- Изменение контракта без перегенерации OpenAPI и SDK (`contracts/openapi/openapi.yaml`,
  `frontend/src/api/generated/`).
- Ломающие изменения API для старых клиентов.
- Текст гостя выводится как HTML (риск XSS).
- Лимиты длины пользовательского текста считаются не в символах (code points), а в единицах
  UTF-16 (`String.length`) или байтах; на границе лимита нет теста с символами вне BMP (эмодзи).
- Права воркфлоу шире нужного или доступ секретов у fork-PR.

## Формат замечания

Каждое замечание содержит:

- **Файл** и **строка**;
- **Условия ошибки** — при каких входных данных или состоянии она проявляется;
- **Последствие** — что увидит пользователь или что сломается;
- **Серьёзность**: `блокирует` / `стоит исправить` / `мелочь`.

## Чего не делать

- Если подтверждённых дефектов нет — написать прямо: **«подтверждённых дефектов нет»**.
  Не придумывать замечания ради объёма.
- Не обсуждать форматирование и стиль: это делает линтер.
- Не выдавать догадку за дефект: замечание должно опираться на код, diff или результат проверки.

## Глубина проверки

Глубина зависит от последствий ошибки.

| Что затронуто | Что проверять |
|---|---|
| Подпись, текст | Соответствие задаче и отображение |
| Слоты, бронирование, конфликты | Основной сценарий, пересечения, соседние случаи, тесты |
| Контракт, API | Обратная совместимость, генерация OpenAPI/SDK |
| Валидация пользовательского ввода | Границы лимитов (N и N+1), в том числе с эмодзи вне BMP: длина считается в символах (code points) |
| Воркфлоу, права | Доступ к коду и секретам, отдельное решение человека |

## Повторное ревью

- Учитывать уже разобранные замечания: смотреть обсуждение PR, не повторять закрытые и
  отклонённые с обоснованием.
- Проверять новые правки (коммиты после предыдущего ревью) — не ломают ли они то, что уже
  было принято.
